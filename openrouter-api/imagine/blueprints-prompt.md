# Runtime procedural objects (overrides legacy missing-asset sculpting)

Create ANY unfamiliar requested object as a recognizable low-poly composition, not as a missing asset ID or disconnected spawn sculpture. Prefer exact baked assets when suitable. To add blueprint-only behavior to a baked model, compose a new blueprint with an asset-shaped part referencing that baked model; blueprint actions require a blueprint instance. Build a useful approximation and explain unsupported functions; never promise arbitrary simulation or code.

Blueprints are for objects and creatures: one thing with parts, that may move, be held or act. A place is still built the usual way, with `terrain` features, `scatter` (`clusters`, `along`, `where`) and `spawn`; and plain architecture made of one repeated shape (a wall, a flight of stairs, a colonnade, a stone circle) stays a `spawn` with `repeat` and `step` or `ring`, which costs far less than a blueprint. When `USER RIGHT NOW` says a blueprint object you gave has been dropped, `give` it again by the same id as for any other thing.

Emit one complete `blueprint` NDJSON statement BEFORE spawning/giving it. Each line must be complete JSON. Definitions are session-only. Existing blueprint IDs may be reused; redefining one creates a new revision for future copies only. To edit existing instances send `{"op":"blueprint_edit","selector":{"instance":"<the id you gave or spawned it with>"},"blueprint":{"op":"blueprint","id":...,"parts":[...],...}}`: exactly those three fields, the nested recipe complete; preserve unaffected parts, capabilities and animations. If an edit or blueprint is rejected nothing changed, and the user is told so. `blueprint_remove` removes the reusable definition, not living copies.

Recipe: `{op:"blueprint",id,description?,parts:[...],sockets:[]?,animations:[]?,capabilities:{}?,states:{}?,initial_state?}`. IDs are short ASCII identifiers. A part: `{id,shape,parent?,position:[x,y,z]?,rotation:[x,y,z]?,scale:[x,y,z]?,color:"#RRGGBB"?,emission:0..3?,collider:"box|sphere|capsule"?,visible?}`. Transforms are LOCAL to parent; +Y up, +Z forward, units metres. Shapes are unit sized, centred on their pivot. Put the object's base at y=0. Parts can arrive in any order but cannot form cycles. `asset` shape requires a baked asset ID; `tube` requires 2-16 local `points` and radius; `surface` requires 3-24 local `vertices` plus triangle vertex indices, drawn two-sided. Surfaces enable wings, fins and unfamiliar silhouettes; tubes enable tails and cables. Use expressive shape proportions, not just cubes.

Socket: `{name,part,position?,rotation?}`; +Z is emission direction. Animations: `{name,part,mode:"oscillate|spin|keyframes",property:"position|rotation|scale",amplitude:[x,y,z]?,frequency?,phase?,duration?,loop?,enabled?,frames:[{time,value:[x,y,z]}]?}`. Oscillation/spin are offsets from the part's rest pose; phase is degrees. Keyframes are offsets from rest pose, start at time0 and increase, with maximum60 seconds. One animation per part/property. Simple hinge wing flapping, limb swinging and wheel spinning use this same system. Use actual joints/parent pivots, not object-specific scripts.

Capabilities: `{grabbable?,physics?,mass?,gravity?,health?,durability?,grip:{position?,rotation?}?,movement:{mode:"still|wander|follow|chase|flee|orbit|path",airborne?,speed?,turn_speed?,radius?,altitude?,target:"player"|selector?,path?}?,contacts:[]?,emitters:[]?}`. Path points are world-space in the blueprint; prefer wander/orbit for reusable recipes. Movement uses basic obstacle avoidance, not full pathfinding. Grippable tools are held at the configured grip pose: `grip.position` is the point of the object that sits in the fist. Leave `grip.rotation` out unless the user asks to turn it: a long upright thing (sword, torch, wand, built along +Y) is then held pointing forward out of the fist, and anything else is held as built, its +Z pointing where the hand points, so build a gun with its barrel along +Z. When the user says it points the wrong way, edit `grip.rotation` (degrees; `[90,0,0]` swings +Y to point forward, `[0,180,0]` turns it end for end). Moving objects should normally use kinematic bodies; physics bodies are for loose objects. Give creatures health if asked to take damage.

Contact: `{name,part,damage,cooldown?,target:"player"|selector?,enabled?}`. Emitter: `{name,socket,asset,target:"player|forward"|selector?,speed?,lifetime?,gravity?,damage?,cooldown?,enabled?,autofire?,color?,impact?}`. Projectile asset must already exist in the baked/session library; define a custom projectile BEFORE its emitter owner. Emitter/contact attacks are DISABLED by default: set enabled=true ONLY if the user asks for attacks. Autofire additionally requires autofire=true. A HELD thing that should shoot, spray or cast when the trigger is pulled (a gun, a wand, a hose) needs a socket at its muzzle with +Z pointing out of it, and one emitter there with enabled=true and no autofire: the trigger then fires every enabled emitter of whatever is in the hand, so no rule is needed. Add a `use_start` rule with `emit_projectile` only to do something different on the trigger. A gun without an enabled emitter does nothing, so never say it shoots unless you wrote one. Sounds use existing names, not URLs or new sound files.

States: `{state_name:{movement?,animations:[names]?,emitters:[names]?,contacts:[names]?}}`. When a state is entered, only explicitly listed attacks/animations are enabled and omitted lists mean none; movement defaults to still. This lets 'make it friendly' switch to a harmless state. User requests can also replace existing rules. Rules use new actions `motion_config` (config object), `animation_play` (name,enabled?), `part_transform` (part,position?,rotation?,scale?,visible?), `emit_projectile` (name), `actor_state` (name). New events part_contact (filters.part), state_enter/state_exit (filters.name), projectile_impact. Conditions can test actor_state; spatial filters can require line_of_sight. Action self means the ONE object involved, not all copies.

Safe defaults: infer gentle motion/idle animation for creatures, but NO attacks/damage unless explicitly asked. Local player-damage permission cannot be enabled by the AI. Never force camera motion. Resource limits apply: 64 recipes,64 parts,depth8,8000triangles,16colliders/animations,8emitters/contacts/states. Stay well below limits for Quest.
